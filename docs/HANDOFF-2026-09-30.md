## 2. Setup 3 — the UCX transport question, settled

**The P→D leg is plain TCP over the 25 GbE management NIC. It is NOT the
AI NIC, and it is not shm.** Established at three independent levels,
because the env alone is ambiguous.

### 2.1 Config

```
UCX_TLS=tcp,rocm,self,sm        UCX_NET_DEVICES=ens50f0
```

Two entries look like contradictions and are not: **`rocm`** is the ROCm
*memory domain* (`rocm_copy`/`rocm_ipc`), present so UCX recognises a HIP
pointer as VRAM rather than host memory — remove it and `registerMem()`
fails (`lib.sh:233`). **`self`/`sm`** are intra-host only and cannot
carry a cross-host leg at all.

### 2.2 Runtime — and a trap worth carrying forward

`rdma resource show qp` shows 5 `VLLM::EngineCor` UD QPs on **`ionic_0`**
on each host — which is exactly the device `creds/setup-3.env` pins for a
future RDMA pass. **They are not ours.** Their pids trace by cgroup to
`aic-vllm-gpu7` (`rocm-aic:kv-repro`, started Sep 15). Our
`kvstack-prefill` / `kvstack-decode` engines hold **zero** QPs.

> **Check the owning pid's cgroup, not the `comm` string.** Same
> shared-host hazard class as the 8080/5600/5601 port collisions already
> in HANDOFF §0.4.

### 2.3 On the wire — measured across a rung-50 handoff

| | ens50f0 (mgmt, 25 GbE) | all 8 `benic*p1` (RoCE fabric) |
|---|---|---|
| prefill | **tx +349.7 MB** | +424 **bytes** |
| decode | **rx +188.3 MB** | +848 **bytes** |

Hundreds of MB on the management NIC; the fabric moved nothing. Note
`ens50f0` carries **both** the P→D leg and the nvme-tcp storage traffic —
one 25 GbE NIC for the entire KV path.

> **Do not try to measure RDMA from `/sys/class/infiniband/*/ports/1/counters/`.**
> ionic exposes only *error* counters under `hw_counters/` and no
> `port_xmit_data`, so a byte count read there is structurally zero and
> proves nothing. Read the RoCE **netdev** counters instead.

### 2.4 Why it cannot simply be switched — the named blocker

`KV_TRANSPORT=rdma` would fail rather than fall back (by design:
`UCX_TLS_RDMA="ib,rocm,self,sm"`, no tcp). And it *would* fail, because
UCX has nothing usable to offer:

```
ud_verbs   ionic_0:1 … ionic_6:1     ← the only IB transport present
rc_verbs   (zero pairs)
```

Root cause is the same named capability setup 4 hit: host
**`rdma-core 39.0-1`**, **`max_srq = 0`** on every ionic device. UCX
filters `rc_verbs` out *before* configuring it. Setup 4 cleared this with
**`rdma-core 61.0-1`** (`max_srq` 0 → 512), after which RC measured
769 Gb/s.

**So HANDOFF §0.6's "setup 3's fabric looks far healthier than setup 4's
ever was" is true about PORT STATE and should not be read as
RDMA-ready.** Ports are ACTIVE, `link_layer: Ethernet`, GIDs present —
but the SRQ gate is shut. On that specific gate, setup 3 sits where setup
4 sat *before* the driver update. The ask is one line: bump `rdma-core`
on both compute hosts.

Note host and container disagree: container carries
`rdma-core 50.0-2ubuntu0.2`, host `39.0-1`. **The host copy is what gates
RDMA availability.** Record both.

### 2.5 Hardware identity (asked separately, recorded here)

```
06:00.0  AMD Pensando Systems DSC3 Salina Upstream Port [1dd8:0008]
09:00.0  AMD Pensando Systems DSC Ethernet Controller  [1dd8:1002]
driver: ionic 25.08.4.004     firmware-version: 1.117.1-a-63
```

`ionic_0…ionic_7` are **not separate cards and not real InfiniBand
HCAs** — they are RoCE HCA functions that `ionic_rdma` registers on top of
each DSC3 Ethernet function via the `ionic.rdma.N` auxiliary devices.
`link_layer` reads **Ethernet**. 7 devices per host; one is DOWN on each
(`ionic_2` on prefill, `ionic_3` on decode).

**On "can an IB interface be programmed with pulsar+vulcano":** not onto
these. The silicon under every one of them is DSC3 Salina, one firmware
slot each. If *Vulcano* means the next-generation 800G UEC AI NIC, that is
different silicon — not a firmware personality for Salina, and the
interface being "IB" changes nothing, since the RoCE function is just a
view onto the same Salina port. If it means a DSC-class firmware bundle
or P4 personality, the gate is ASIC compatibility and the image declares
it — **I could not resolve which was meant.** Nothing named `pulsar` or
`vulcano` exists in this repo or under `/opt`/`/usr/local` on the compute
hosts, and no Pensando userspace tooling (`pdsctl`, `dsctool`,
`nicmgrctl`) is installed, so even a correct flash would need tooling that
is not on those boxes. **Caution:** the `aic-*` stack has been running on
these NICs for weeks and owns all current RDMA QPs — reflashing a port
takes their traffic down with ours.

**The one to understand is `c63951b`.** `exec 3>&- 2>/dev/null || true`
appeared at four sites. A redirection written on `exec` with no command
alters the **shell's own** fd table, permanently — so that `2>/dev/null`
did not scope to the close, it rebound fd 2 for the rest of the script.

fired on the **success** path of `wait_for_port`, which gates
`start-vllm.sh` twice. So `start-vllm.sh` could pass its daemon gate and
then **die with no output at all** — already observed on setup 4
(2026-09-29, smc2: *"decode died at exit 1 with ZERO output"*).

### 6.2 `--cap-add SYS_ADMIN` — unresolved, do not copy blind

The setup-3 branch's headline root cause: without `CAP_SYS_ADMIN` the
kernel permits `KV_STORE`/`KV_RETRIEVE` (they alias write/read) but denies
`KV_EXIST`/`KV_DELETE` with `-EACCES`, so the tier stores perfectly and
misses 100% of lookups — indistinguishable from a cold cache, because
`queryMem()` degrades errors to "absent" by design.

**Why I did not port it:** the kernel gate is in the generic NVMe
passthrough path, so it *should* apply to setup 4 as well — yet setup 4
demonstrably recorded `l2_device_hits=4` at rung 60 without the
capability. Something about that path differs and I could not explain it.

## 7. Traps this session re-confirmed

- **`ss -tlnp | grep -w ":8080"` gives false "free" readings.** `-w`
  treats `:` as a word boundary. Use
  `ss -tlnp | awk -v P=":8080$" '$4 ~ P'`.
- **A co-tenant's QPs appear under `comm VLLM::EngineCor`** on the very
  device your creds pin. Check the cgroup.
- **`/var/log/kvstack/` exists on the host and is not the log you want** —
  it holds build/download logs. The real ones are inside the container.
- **`docker load` recomputes the image config**, so top-level image IDs
  legitimately differ across hosts. Compare `RootFS.Layers` and `Config`.
- **Rung 50 from the control host is a FALSE FAIL** on a healthy stack.
- **Rung 60 recreates both containers**, destroying anything
  pip-installed in them — run it *before* §4's llama-benchy, not after.
